01 // The stack

The core stack

  • BBedrockAI models Our photo analyzer runs models like Claude Sonnet here. No servers to run.
  • LLambdaCompute One function each for the API, the authorizer and every worker.
  • AAPI GatewayFront door One entry point. It checks each device token.
  • NNode.jsRuntime Plain JavaScript. The TypeScript compiler checks its JSDoc types.
  • DDynamoDBData One table, defined in Terraform.

Also in the stack: custom elements and Web Awesome, Vite, SQS, S3, CloudFront and WAF, Cognito, Terraform, GitHub Actions.

02 // Foundation

Built on the City's SDLC standard

We follow Level 2 of the CCSF Software Development Lifecycle Standard.

  • Everything in Git Code, infrastructure, pipelines, docs and config.
  • Terraform only Remote state with locking. Plan and apply run in CI, never from a laptop.
  • Tagged resources Seven CCSF tags on every cloud resource.
  • No secrets in source Code points to Secrets Manager and Parameter Store.
  • Managed services Each has only the IAM access it needs.
  • Hardened edge TLS 1.2+, HSTS, CSP, CloudFront, WAF and rate limits.
  • Core Web Vitals A bundle size budget and Lighthouse run on every pull request.
  • Accessibility WCAG 2.2 AA target. Browser tests run axe checks.

Checklist: docs/sdlc-level-2-checklist.md

04 // Frontend

Frontend

No framework. Keeping the JavaScript small is how we meet Core Web Vitals.

  • Native custom elements The browser's own component model.
  • Web Awesome Shared form controls, icons, spinners and callouts. Buttons are native.
  • Vite build with budgets Each route loads as its own chunk. CI checks a size limit on each. Main bundle: 77.3 kB JS, 22 kB CSS.
  • Installable A web app manifest and an install prompt put it on the home screen.
  • Opens offline A Workbox service worker precaches the built app. It never handles API calls.
  • Offline queues The device saves care work logs and perimeter checks. It sends them when the connection returns.

06 // Local development

A local environment that mirrors AWS

npm run dev runs the same Lambda code against local stand-ins for DynamoDB, SQS and S3.

  • Same Lambda code A local router builds API Gateway events and calls the handlers directly. Workers poll the local queue.
  • DynamoDB Local The single table, created and seeded on first run.
  • SQS and S3 ElasticMQ and MinIO, through the same AWS SDK clients.
  • No Docker, no AWS login Needs only Node and a Java runtime. Works offline.
  • Stubbed services Local stand-ins for the authorizer, the photo analyzer and 311.
  • Tests use it too The browser tests start their own copy of the stack on their own ports.

We check cloud wiring (IAM, API Gateway mappings, queue triggers) in the dev environment. Decision record: docs/adr/0006-docker-free-local-dev-harness.md

07 // Working with agents

Development workflow

  1. Write A person and an AI agent write the change together.
  2. First review They review it before it leaves the laptop.
  3. Second review A separate agent reviews the pull request.
  4. CI Automated checks run, then the merge deploys to dev.
  • Agents never commit or push A person stages and commits every change.
  • Disclosure review, every handoff The agent checks its changes for secrets and personal data before calling them ready.

The rules for agents live in AGENTS.md.

09 // Delivery

Deploys and AWS access

Two branches, two environments dev + prod

  • dev branch: every merge deploys to dev.
  • main branch: a published v* release deploys to prod once a named reviewer approves.

OIDC, not access keys GitHub to AWS

  • GitHub Actions trades a short-lived token for a deploy role. We store no long-lived keys.
  • Each environment has its own role. Only its own GitHub Environment can use it.
  • The job stops if it lands in the wrong AWS account.

Decision record: docs/adr/0007-deploy-promotion-model.md

10 // Operations

Observability

  • Metrics are log lines We write business metrics in CloudWatch's embedded format. Every data point is also a searchable event with its ids.
  • One ops dashboard Alarm status first, then activity, analyzer, queues and API. The charts show alarm thresholds.
  • One email per incident Related failures share one alarm.
  • Daily warning digest Minor failures arrive in one email.
  • Outside-in uptime Route 53 checks /health through the full path.
  • A runbook per alarm Each one says where to look first.

CloudWatch is the source of truth. PostHog only carries client errors and feedback.
